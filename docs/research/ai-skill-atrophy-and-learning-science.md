# AI-assisted coding, skill atrophy, and the learning science of building real skill

Research notes for the `learn-to-build` skill. Compiled 2026-10-11 from primary sources (papers, arXiv, publisher/DOI pages, Anthropic and METR posts). Every claim links to its source.

**Evidence grades**
- **A**: several RCTs or a meta-analysis; replicated.
- **B**: one well-designed RCT, or a consistent set of smaller experiments.
- **C**: small-N, preprint, correlational, self-report, or qualitative.
- **D**: position paper, theory, or vendor telemetry. Useful for framing, but not evidence of an effect.

---

## Part A: Evidence on AI and skill

### A1. Anthropic, "How AI assistance impacts the formation of coding skills" (Shen & Tamkin, Jan 2026). Grade B, the most directly relevant study

- **Design.** RCT with [52 mostly junior engineers](https://www.anthropic.com/research/AI-assistance-coding-skills): 26 in the AI condition and 26 in the no-AI condition. Each had used Python at least weekly for over a year and had never used **Trio** (async Python). They had [35 minutes to build two Trio features](https://arxiv.org/html/2601.20245v2) from a problem description, starter code, and a short concept explainer, and they were told a quiz would follow. The AI group had a sidebar chat assistant ([GPT-4o](https://arxiv.org/html/2601.20245v2)) that could see their code and produce correct code on request. This is a chat assistant, not an agent. [The authors expect agentic tools like Claude Code to affect skill development more strongly](https://www.anthropic.com/research/AI-assistance-coding-skills).
- **Outcome.** A quiz covering debugging, code reading, code writing, and conceptual understanding. The AI group scored [50% vs 67%, Cohen's d = 0.738, p = 0.01](https://www.anthropic.com/research/AI-assistance-coding-skills), which is 4.15 points on a 27-point quiz. [The effect held after controlling for warm-up time (d = 0.725)](https://arxiv.org/html/2601.20245v2). **The largest gap was in debugging** and the smallest in code reading ([paper](https://arxiv.org/html/2601.20245v2)).
- **Speed.** The AI group was about 2 minutes faster, which was [not significant](https://www.anthropic.com/research/AI-assistance-coding-skills). Some participants spent [up to 11 minutes (30% of the time) writing queries](https://www.anthropic.com/research/AI-assistance-coding-skills).
- **Errors as the mechanism.** The median number of errors hit was [1 with AI vs 3 without](https://arxiv.org/html/2601.20245v2). The authors argue that resolving Trio-specific errors yourself is what built skill: "encountering errors may play a significant role in the formation of coding skills" ([paper](https://arxiv.org/html/2601.20245v2)).
- **Interaction patterns.** These are qualitative, come from screen recordings, and are explicitly *not causal*. Cells are small, n = 2 to 7 ([post](https://www.anthropic.com/research/AI-assistance-coding-skills)).

  | Pattern | n | Avg quiz score |
  |---|---|---|
  | AI delegation (AI writes everything) | 4 | <40% |
  | Progressive reliance (asks a few questions, then delegates) | 4 | <40% |
  | Iterative AI debugging (AI fixes or verifies code instead of explaining it) | 4 | <40% |
  | Generation-then-comprehension (gets code, then asks follow-ups to understand it) | 2 | ≥65% |
  | Hybrid code + explanation (asks for code *with* explanations) | 3 | ≥65% |
  | **Conceptual inquiry** (asks only conceptual questions and fixes errors alone) | 7 | ≥65%, and second-fastest overall |

  Takeaway: **what preserved learning was cognitive engagement**, meaning the learner did the explaining, debugging, or deciding. Abstaining from AI was not required. The pattern that worked best and was most common, conceptual inquiry, maps directly onto a tutor that answers "why/how does X work" but doesn't write the code.
- **Limitations stated by the authors** ([post](https://www.anthropic.com/research/AI-assistance-coding-skills)): small N; the quiz came immediately after the task, so there is no retention data; patterns are not causal; one library; GPT-4o chat rather than agents.

### A2. MIT Media Lab, "Your Brain on ChatGPT" (Kosmyna et al., 2025). Grade C

- **Design.** Essay writing in three groups: LLM, search engine, and brain-only. [54 participants did three sessions; 18 did a fourth crossover session](https://arxiv.org/abs/2506.08872) in which the LLM group wrote unaided and vice versa. Measures were EEG connectivity, NLP analysis of the essays, and teacher and AI-judge scoring.
- **Findings.** ["Brain connectivity systematically scaled down with the amount of external support"](https://www.media.mit.edu/projects/your-brain-on-chatgpt/overview/). LLM users had trouble quoting essays they had written minutes earlier and reported the lowest ownership. In session 4, LLM-to-brain participants showed weaker alpha and beta connectivity, while **brain-to-LLM participants showed higher recall** ([project page](https://www.media.mit.edu/projects/your-brain-on-chatgpt/overview/)). That last result is the one most useful for design: *think first, then use AI* did better than the reverse.
- **Limitations.** Small sample (n = 18 for the key crossover), from one region; ChatGPT only; essays only; EEG cannot localise deep structures; [non-peer-reviewed preprint](https://www.media.mit.edu/projects/your-brain-on-chatgpt/overview/). The authors explicitly ask the press not to describe the results as "brain rot," "dumber," or "brain damage" ([FAQ](https://www.media.mit.edu/projects/your-brain-on-chatgpt/overview/)). The paper is not about coding, and EEG connectivity is not a measure of skill.

| [Lee et al., CHI 2025 (Microsoft/CMU)](https://doi.org/10.1145/3706598.3713778) | Survey, 319 knowledge workers, 936 examples | **Higher confidence in GenAI → less critical thinking; higher self-confidence → more.** Critical thinking shifts to verification, integration, and stewardship. | C (self-report, cross-sectional) |

| [METR update, Feb 2026](https://metr.org/blog/2026-02-24-uplift-update/) | 57 developers, 800+ tasks, late-2025 tools | Estimates of −18% and −4% time (speedup); **all CIs include zero**. 30–50% of developers withheld tasks they wouldn't do without AI. METR calls the data "very weak evidence." | C |
| [Appelt & Glauben, PACIS 2026](https://aisel.aisnet.org/pacis2026/ai_fow/ai_fow/13) | Controlled experiment, 24 developers, Copilot Ask vs Agent | Agent: −61.7% time and −57.4% workload, with **no significant gain in correctness**. Developers moved from active collaboration to "passive supervision." | C |
| [Yu & Moon, AIES 2026](https://arxiv.org/abs/2607.17067) | Interviews, N = 14, Korean junior and senior engineers | "Absorption": GenAI takes over entry-level work, and **juniors lose the productive struggle** that used to make them seniors | C (qualitative) |
| [Mehra et al., ASE NIER 2026, "Agents That Teach"](https://arxiv.org/abs/2607.06101) | Position paper | "Knowledge Debt" means agent-made changes the developer doesn't understand. Incidental learning "must be deliberately designed" back in, delivered out-of-band so it doesn't break flow. | D |
| [Anthropic, Claude Code usage, Apr 2025](https://www.anthropic.com/research/impact-software-development) | Telemetry | Claude Code conversations are **79% automation** vs 49% on Claude.ai. The "Learning" augmentation share is much lower in Claude Code. | D (describes behaviour, not outcomes) |
| [Anthropic Education Report, Apr 2025](https://www.anthropic.com/news/anthropic-education-report-how-university-students-use-claude) | Telemetry | About 47% of student conversations were "Direct" (answer-seeking). Claude's responses were mostly *Creating* (39.8%) and *Analyzing* (30.2%), which are the higher-order work being offloaded. | D |

**Background theory (automation).** Grade B for the review; the mechanism is long established. [Parasuraman & Manzey 2010](https://doi.org/10.1177/0018720810376055) reviewed the automation-complacency and automation-bias literature. Both appear in novices *and* experts and are **not fixed by training or instructions alone**. [Bainbridge's "Ironies of Automation" (1983)](https://doi.org/10.1016/0005-1098(83)90046-8) argues that automating the routine part removes the practice operators need to handle the exceptions. [Risko & Gilbert 2016](https://doi.org/10.1016/j.tics.2016.07.002) frame offloading as a metacognitively driven choice.

### A4. What is robust and what is weak

- **Robust (B+):** Unrestricted AI help while *learning* something new lowers unaided performance afterwards. Two independent RCTs show this in different domains ([Shen & Tamkin](https://arxiv.org/abs/2601.20245); [Bastani](https://doi.org/10.1073/pnas.2422633122)). **How the AI is used moderates the effect:** answer-withholding tutors and engaged usage patterns remove most of the harm ([Bastani](https://doi.org/10.1073/pnas.2422633122); [Kazemitabaar 2025](https://arxiv.org/abs/2410.08922); [Shen & Tamkin patterns](https://www.anthropic.com/research/AI-assistance-coding-skills)).
- **Fairly robust:** People misjudge AI's effect on their own performance or understanding ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [Prather](https://arxiv.org/abs/2405.17739)). Feeling productive is not the same as learning.
- **Weak:** Long-term "atrophy" of skills you *already have*. No longitudinal RCT exists. The evidence is correlational ([Gerlich](https://doi.org/10.3390/soc15010006)), self-reported ([Lee](https://doi.org/10.1145/3706598.3713778)), qualitative ([Yu & Moon](https://arxiv.org/abs/2607.17067)), or neural proxies in a small preprint ([Kosmyna](https://arxiv.org/abs/2506.08872)). All the RCTs measure *acquisition* soon after the task, not decay. The "brain rot" framing goes beyond the data.
- **Contrary signal:** [Kazemitabaar 2023](https://doi.org/10.1145/3544548.3580919) found AI access *did not hurt* novices' manual or retention performance on a structured platform, so the harm is not inevitable.

## Part B: Learning-science mechanisms, and what each means for an AI tutor

| Mechanism | One-line claim | Evidence | Implication for exercise generation |
|---|---|---|---|
| **Generation effect** | Producing an answer yourself beats reading it. | A: [Slamecka & Graf 1978](https://doi.org/10.1037/0278-7393.4.6.592); meta-analysis [d = .40 over 86 studies](https://doi.org/10.3758/BF03193441), with larger effects at longer retention intervals. **Boundary:** for novices on high-element-interactivity material, studying examples beats generating ([Chen, Kalyuga & Sweller 2015](https://doi.org/10.1037/edu0000018)). | The learner must *produce the core logic* (the algorithm, the state transitions, the async coordination). Never let generation shrink to a one-line `TODO` while the AI writes the interesting parts. When the material is too complex for the learner yet, show a worked example first (see fading). |
| **Retrieval practice / testing effect** | Recalling from memory beats re-studying, especially after a delay. | A: [Roediger & Karpicke 2006](https://doi.org/10.1111/j.1467-9280.2006.01693.x); meta-analyses [Rowland 2014](https://doi.org/10.1037/a0037559) (recall tests > recognition) and [Adesope et al. 2017](https://doi.org/10.3102/0034654316689306) (tests beat restudy and every other comparison); rated "high utility" by [Dunlosky et al. 2013](https://doi.org/10.1177/1529100612453266). | Open sessions with "write X from memory" or "explain why Y happened" before showing any reference. Prefer free recall and code-from-blank over multiple choice. Close with a no-AI recall check. |
| **Spacing** | Spreading practice over time beats massing it, and the best gap grows with the retention goal. | A: [Cepeda et al. 2006](https://doi.org/10.1037/0033-2909.132.3.354) (839 assessments); spaced retrieval vs massed [g = 0.74](https://doi.org/10.1007/s10648-020-09572-8), with no clear advantage for expanding over uniform schedules ([Latimier et al. 2021](https://doi.org/10.1007/s10648-020-09572-8)). | Keep a per-learner concept log and resurface earlier concepts in later projects (for example, re-implement a cancel scope a week later). A simple fixed schedule is fine. Don't over-engineer the SRS. |
| **Desirable difficulties** | Conditions that slow learning now (spacing, interleaving, testing, variation) often improve retention and transfer, but only if the learner can meet them. | A (as an umbrella for the above): [Bjork & Bjork 2011](https://bjorklab.psych.ucla.edu/wp-content/uploads/sites/13/2016/04/EBjork_RBjork_2011.pdf) | Accept slower sessions. Don't let the AI "rescue" the learner at the first stall. If the learner lacks the prerequisites, the difficulty is *undesirable*, so scaffold. |
| **Productive failure** | Attempting a problem *before* instruction, then getting instruction, beats instruction-first for conceptual understanding. | A−: meta-analysis of 53 studies, [g = 0.36 [0.20, 0.51]; 0.37–0.58 with high fidelity to PF design](https://doi.org/10.3102/00346543211019105). Reversed for young children and domain-general skills. Original: [Kapur 2008](https://doi.org/10.1080/07370000802212669). | For a new concept, pose the problem first ("how would you stop 3 tasks when one fails?"), let the learner try a naive version, *then* teach the idiom while contrasting it with their attempt. Instruction must follow the attempt, because unresolved failure is not productive. |
| **Worked examples and fading** | Novices learn more from studying worked solutions than from unguided problem solving. Gradually removing steps eases the move to independent solving. | A: [Sweller & Cooper 1985](https://doi.org/10.1207/s1532690xci0201_3); [Atkinson et al. 2000 review](https://doi.org/10.3102/00346543070002181); fading: [Renkl & Atkinson 2003](https://doi.org/10.1207/S15326985EP3801_3). Subgoal labels have mixed results in CS ([Morrison et al. 2015](https://doi.org/10.1145/2787622.2787733)). | Use a ladder: full example with labelled subgoals → example with the *key* step blanked → learner writes it all. **What gets faded must be the conceptually central step**, not boilerplate. Fade as the learner succeeds. |
| **Expertise reversal** | Guidance that helps novices becomes redundant, or harmful, for more expert learners. | A−: [Kalyuga et al. 2003](https://doi.org/10.1207/S15326985EP3801_4) | Calibrate scaffolding to the learner, starting with a diagnostic. An experienced developer learning Trio needs a problem first, not a walkthrough of Python syntax. Remove scaffolds quickly once the learner shows competence. |
| **Parsons problems** | Reordering scrambled code teaches about as well as writing it, in less time. | B: [Ericson et al. 2017](https://doi.org/10.1145/3141880.3141895) found no difference in learning or one-week retention vs writing or fixing code, and it was faster. Review: [Ericson et al. 2022 ITiCSE WG](https://doi.org/10.1145/3571785.3574127). Hierarchy of tracing and Parsons → writing: [Lopez et al. 2008](https://doi.org/10.1145/1404520.1404531). | Good as a *bridge* rung for a new construct, especially with distractor lines that encode common misconceptions. It's not the end goal: follow it with from-scratch writing. |
| **PRIMM** (Predict, Run, Investigate, Modify, Make) | A structured progression from reading to writing improves attainment. | B−: 13 schools, 493 students aged 11–14, PRIMM beat a control group on the post-test ([Sentance et al. 2019](https://doi.org/10.1080/08993408.2019.1608781)). Related: teaching tracing → syntax → templates → writing improved outcomes ([Xie et al. 2019](https://doi.org/10.1080/08993408.2019.1565235)). | A ready-made session template: show code → learner **predicts** output → runs it → investigates the surprise → modifies it → makes something new. The "Make" step is mandatory and must be substantial. |
| **Deliberate practice** | Expertise grows through effortful practice aimed at specific weaknesses, with feedback. | Theory A, but effect-size B: [Ericsson et al. 1993](https://doi.org/10.1037/0033-295X.100.3.363). Meta-analysis: practice explains [26% of variance in games, 4% in education, <1% in professions](https://doi.org/10.1177/0956797614535810). | Aim each exercise at a diagnosed weakness, at the edge of ability, with immediate feedback (tests). Don't promise that "10,000 hours" will turn anyone into a programmer. |
| **Interleaving** | Mixing problem types beats blocking for learning to *discriminate* which approach applies. | B: meta-analysis [g = 0.42 overall, 0.34 for math; blocking better for words](https://doi.org/10.1037/bul0000209). Little programming-specific evidence. | After single-concept drills, give mixed tasks where the learner must *choose* the tool (task group vs cancel scope vs channel). Works best when categories are similar enough to confuse. |
| **Self-explanation** | Explaining *why* each step works improves learning, and good learners do it spontaneously. | A: [Chi et al. 1989](https://doi.org/10.1207/s15516709cog1302_1); meta-analysis [g = .55 over 64 reports](https://www.Gwern.net/doc/psychology/spaced-repetition/2018-bisra.pdf) ([DOI](https://doi.org/10.1007/s10648-018-9434-x)), whose authors explicitly recommend *computer-generated* prompts. | Whenever the AI shows code, require the learner to explain it ("why does this need `async with`?") before moving on. This is the "generation-then-comprehension" pattern that preserved learning in [Shen & Tamkin](https://www.anthropic.com/research/AI-assistance-coding-skills). |
| **Metacognition and calibration (predict before run)** | Novices misjudge their own understanding, and AI makes this worse. Explicit monitoring prompts help. | B−: an explicit problem-solving process and self-monitoring prompts raised independence and metacognitive awareness ([Loksa et al. CHI 2016](https://doi.org/10.1145/2858036.2858252)). "Illusion of competence" with AI ([Prather 2024](https://arxiv.org/abs/2405.17739)). Developers misjudged their AI speedup ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Restudying inflates confidence ([Roediger & Karpicke](https://doi.org/10.1111/j.1467-9280.2006.01693.x)). | Before every run, ask "what will this print or raise?" and record confidence. Score predictions against outcomes and show the learner their calibration over time. Before a session ends, run a no-AI checkpoint so the learner knows what they can actually do. |

**On AI tutors specifically.** Grade B. Step-based tutoring systems reach [d = 0.76, close to human tutors at 0.79](https://doi.org/10.1080/00461520.2011.611369) ([VanLehn 2011](https://doi.org/10.1080/00461520.2011.611369)). A physics RCT with an AI tutor built on pedagogical best practices (active learning, cognitive-load management, sequential scaffolding, pre-written step solutions, timely feedback, self-pacing) produced [0.73–1.3 SD larger gains than active-learning lectures, in less time](https://pmc.ncbi.nlm.nih.gov/articles/PMC12179260/). It was a two-week study at one institution, and the authors flag "when to give answers vs guide" as an open question. The pedagogy, not the model, is what does the work.

**Relevant prior art: the Claude Code "Learning" output style.** It [handles routine implementation itself and leaves "a few lines" marked `TODO(human)`](https://code.claude.com/docs/en/output-styles) at design decisions. This is useful for incidental learning during real work. However, it is close to the failure mode this skill is meant to avoid: the AI holds the plan and the learner fills in small gaps. `learn-to-build` should invert the ratio.

## Part C: Design principles for `learn-to-build`

1. **The learner writes the load-bearing code.** The algorithm, control flow, and concurrency logic are written by the learner. The AI may write only incidental scaffolding the learner already knows (I/O, boilerplate, test fixtures), and should say so. Grounds: generation effect; delegation patterns scored below 40% in [Shen & Tamkin](https://www.anthropic.com/research/AI-assistance-coding-skills).
2. **The AI asks before it tells.** Default to conceptual Q&A and Socratic hints. Never give full solutions unless the learner explicitly gives up, and even then follow up with a re-do from scratch. Grounds: [Bastani](https://doi.org/10.1073/pnas.2422633122) (hint-only removed the harm); conceptual inquiry was the best pattern.
3. **Attempt first, then instruct.** Pose the problem, let the learner try something naive, then teach the idiom while contrasting it with their attempt ([productive failure](https://doi.org/10.3102/00346543211019105); brain-first-then-AI in [Kosmyna](https://www.media.mit.edu/projects/your-brain-on-chatgpt/overview/)). Scaffold more heavily for true novices on complex material ([Chen et al. 2015](https://doi.org/10.1037/edu0000018)).
4. **Stepwise and learner-led.** For multi-step tasks, the learner states what each step must do before any code for it appears ([Kazemitabaar 2025](https://arxiv.org/abs/2410.08922)).
5. **Let errors happen and leave the debugging to the learner.** Don't pre-empt bugs, and don't fix them. Ask diagnostic questions instead. Error resolution is probably where the debugging skill gap came from ([Shen & Tamkin](https://arxiv.org/html/2601.20245v2)).
6. **Fade scaffolding adaptively.** Diagnose prior knowledge first. Move from worked example → blanked *key* step → Parsons → from scratch, and skip rungs for experienced learners ([fading](https://doi.org/10.1207/S15326985EP3801_3); [expertise reversal](https://doi.org/10.1207/S15326985EP3801_4)).
7. **Predict, explain, recall.** Before running code, the learner predicts the outcome. After seeing AI code, they explain it. At the start of each session, they recall earlier material ([PRIMM](https://doi.org/10.1080/08993408.2019.1608781); [self-explanation](https://doi.org/10.1007/s10648-018-9434-x); [retrieval practice](https://doi.org/10.3102/0034654316689306)).
8. **Make calibration visible.** Track predicted vs actual results and finish each project with a no-AI checkpoint. Feeling productive is unreliable ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [Prather](https://arxiv.org/abs/2405.17739); [Lee](https://doi.org/10.1145/3706598.3713778)).
9. **Space and interleave across projects.** Resurface earlier concepts and mix problem types so the learner must choose the right tool ([spacing](https://doi.org/10.1007/s10648-020-09572-8); [interleaving](https://doi.org/10.1037/bul0000209)).
10. **Enforce the ratio structurally.** Prompts alone are not enough. Complacency is [not fixed by instructions](https://doi.org/10.1177/0018720810376055), and the Claude Code docs note that output-style instructions are [not guaranteed](https://code.claude.com/docs/en/output-styles). Use checks the learner can see, such as tests the learner's code must pass and diffs that show who wrote which lines.

**Anti-pattern checklist (reject an exercise if any is true):** the AI wrote the core logic; the learner's part is under about 20% of the meaningful lines or is mechanical; the instructions name the exact API call to use; there is no prediction or explanation step; the exercise can be passed by pasting the task into a chatbot.

### ADHD and attention (weaker evidence, flagged)

- **Grade C for adult programmers.** A review of 22 studies (N = 1,181 *children*) found that reinforcement improves task performance in AD/HD and controls, somewhat more in AD/HD, and that children with AD/HD [**prefer immediate over delayed reward**](https://doi.org/10.1016/j.cpr.2004.11.001) ([Luman et al. 2005](https://doi.org/10.1016/j.cpr.2004.11.001)). I found no RCT on ADHD adults learning to program with AI tutors.
- **Reasonable but unproven design:** short, testable increments with immediate pass/fail feedback; one visible goal at a time; resumable state so interruptions are cheap. Good tutoring already does these things ([VanLehn](https://doi.org/10.1080/00461520.2011.611369); [Kestin et al.](https://pmc.ncbi.nlm.nih.gov/articles/PMC12179260/) "timely feedback," "self-pacing"). Treat them as accessibility defaults, not as evidence-based ADHD interventions.
- **Tension:** fast feedback must not turn into "AI fixes it instantly." The feedback should come from the learner's own test run, not from the AI handing over an answer.
